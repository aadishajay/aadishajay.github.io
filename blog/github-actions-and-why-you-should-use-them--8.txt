14:Td5d,<p>A few years back , my team at letsgoforacamp.com was delivered a dashboard , which would make their operations more streamlined. It was written using a PHP Framework called CodeIgniter.</p>
<p>As in almost any other project things went pretty stable in the beginning , the dashboard served its purpose. And then , as business grew , new changes needed to be put in. The development team would develop things over the production server , test it over there. Testing was done on production , connecting over a file manager provided by the hosting service and many a times things broke and got fixed.</p>
<p>This cannot be the case when it comes to a mission-critical software. You cannot develop over the production code and just wish nothings gonna break! So , in came version control via GIT , we used GitHub. The code was developed over local machines of the developers , tested there and then pushed over to the repository in GitHub. Then the developers would login to the production server and "pull" the production branch in the sever and voila! the change is deployed.</p>
<p>Imagine if your team if of many developers and allowing everyone to allow accessing production sever just to get the bug fixes or features deployed is a security red-flag. So , we looked out to what the industry does. <a href="https://www.synopsys.com/glossary/what-is-cicd.html#:~:text=CI%20and%20CD%20stand%20for,are%20made%20frequently%20and%20reliably.">CI/CD</a> was the answer. That's all about setting up a process which involves two parts :</p>
<ol>
<li>Continuous Integration: Which we had almost implemented. Separating code versions into branches and then merging it onto a single source of truth prod branch , provided all testing is done in a lower environment.</li>
<li>Continuous Deployment : This is more or less a contribution from the Agile and DevOps world. Once your new version of code is checked in to production branch , it needs to be built , bundled and deployed into the production server(s)</li>
</ol>
<p>In our case , things were merely simple , as we were using PHP and needn't do any sort of  build activity. We just had to make sure that the production branch code is pulled into the production server.</p>
<h2>Github Actions and Runners to the rescue</h2>
<p>A little bit of research helped us to implement <a href="https://github.com/features/actions">Github actions</a> , and configure it so that it runs whenever we do a check in to the production branch of code (the right way would be to do a pull request) . The Github action would check out the prod version of code and then connect to the production server over SSH and would run a script there , that would do the "pull" part - simple as that. And now, the team just has to do a pull request over any neat and sanity checked branch and in a few moments the code is in production. The crux of GitHub actions are GitHub runners , we can imagine then to be on demand virtual machines that do the work for you. You may chose and OS of your like say Ubuntu , Mac or Windows.</p>
<h2>Where to start ?</h2>
<p>Check out the extensive documentation given on <a href="https://github.com/features/actions">Github actions</a>  and also in the actions tab of every GitHub repositories. There is a whole bunch of things you can actually get done.</p>
<p>So , yeah , happy learning mates.
Well , even this blog is powered by GitHub Actions and Runners. ;)</p>
